01

Introduction

This Software Requirements Specification defines the functional and non-functional requirements for EpicHub — a two-sided event vendor marketplace for the Egypt and MENA region. It follows IEEE 830 structure and serves as the primary reference for development, testing, and project sign-off.

1.1 Purpose

The purpose of this document is to describe the behavior of the EpicHub system in sufficient detail that development teams can build it, QA teams can test it, and stakeholders can validate it. Requirements in this document are the source of truth for what the system must and must not do.

1.2 Scope

This SRS covers the Phase 1 EpicHub platform — the customer-facing marketplace, vendor portal, and internal operations CMS. It does not cover the corporate enterprise module, mobile native applications, or Arabic RTL interface (all deferred to Phase 2).

1.3 Definitions & Abbreviations

TermDefinition
ApplicationUserThe .NET Identity user entity — extended with RefreshToken fields. Shared base for all user types.
VendorA business entity providing event services (photography, catering, etc.) on the platform.
EventA customer-created planning container with a date, type, and budget. Can hold many EventItems.
EventItemA single draft service (Product or Package) added to an Event. Price is snapshotted at add time.
OrderThe financial record created when a customer checks out from an Event. Links back to the Event via EventId FK.
OrderItemA financial line item within an Order. Snapshots name and price from the corresponding EventItem.
EscrowPayment held by the platform from booking confirmation until delivery confirmation.
GMVGross Merchandise Value — total value of all transactions processed through the platform.
FRFunctional Requirement — a statement of required system behavior.
NFRNon-Functional Requirement — a quality attribute of the system (performance, security, etc.).
UCUse Case — a numbered scenario describing actor-system interaction.
02

System Overview

2.1 Product Perspective

EpicHub is a standalone web application consisting of three logical sub-systems: the Customer Portal (Angular SPA), the Vendor Portal (Angular SPA, separate route domain), and the Operations CMS (Angular SPA, admin subdomain). All three consume a shared ASP.NET Core REST API backend with a single SQL Server database and Redis cache layer.

System Boundary

The EpicHub system boundary includes: the Angular frontends, the .NET 8 API, the SQL Server database, the Redis cache, the SignalR real-time hub, and all integration adapters (payment gateway, email, SMS, chatbot). It excludes: the payment gateway itself, the email/SMS providers, and the AI model provider (OpenAI).

2.2 User Classes & Characteristics

CustomerSearches, plans events, and books vendor servicesAuthenticated — Customer roleLow — consumer-facing UI required
VendorManages services, calendar, and incoming bookingsAuthenticated — Vendor roleMedium — dashboard power user

GuestBrowses public vendor profiles without bookingUnauthenticatedLow — read-only access

2.3 Operating Environment

The system must operate on: Chrome ≥ 110, Firefox ≥ 110, Safari ≥ 16, Edge ≥ 110 on desktop. Chrome ≥ 110, Safari ≥ 16 on mobile. Backend hosted on Azure App Service (.NET 8, Linux). Database on Azure SQL. Frontend on Azure Static Web Apps with CDN.

03

Functional Requirements

All functional requirements are uniquely identified and assigned a MoSCoW priority. Each requirement is atomic — it describes exactly one system behavior. Requirements trace to Use Cases where applicable.

3.1 Authentication & Authorization

FR-A01
MUST

User Registration

The system shall allow users to register with email and password. Passwords must be hashed using ASP.NET Identity's BCrypt pipeline. A verification email shall be sent upon registration.

UC-01: New User Registration
FR-A02
MUST

JWT Authentication

The system shall issue a JWT access token (15-minute expiry) and a refresh token (7-day expiry) upon successful login. Refresh tokens are stored server-side and invalidated on logout.

FR-A03
MUST

Role-Based Authorization

The system shall enforce role-based access control with three roles: Customer, Vendor, and Admin. API endpoints are decorated with role-specific authorization attributes. A user may hold one role only.

FR-A04
SHOULD

OAuth 2.0 Social Login

The system shall support Google OAuth 2.0 as an external login provider. Social accounts are linked to a locally created ApplicationUser record.

FR-A05
MUST

Password Reset

The system shall support a password reset flow: user requests reset by email → receives time-limited token → submits new password. Tokens expire after 1 hour and are single-use.

3.2 Search & Discovery

FR-S01
MUST

Vendor Search with Filtering

The system shall allow customers to search vendors by: category (FK to Category), event type, location string, date range, and price range. Results shall be returned within 2 seconds. Pagination: 20 results per page.

UC-05: Customer searches for vendors
FR-S02
MUST

Availability Filter

The search endpoint shall accept an event date parameter and exclude vendors who have blocked that date on their availability calendar. Availability data is read from Redis cache (TTL: 60 seconds).

FR-S03
MUST

Matchmaking Score

Search results shall be ranked by a computed matchmaking score: availability match (40%) + vendor rating (35%) + category match (25%). Score is computed server-side. Customers cannot see the raw score.

FR-S04
MUST

Vendor Profile Page

The system shall serve a public vendor profile page displaying: BusinessName, Description, IsVerified badge, VendorRatings, portfolio images (from Azure Blob), service list with prices, and a 30-day availability calendar preview. This page is accessible to unauthenticated users.

FR-S05
SHOULD

Shortlist Feature

Authenticated customers shall be able to add up to 5 vendors per category to a persistent shortlist stored in the database. A comparison view shall display up to 5 shortlisted vendors side by side.

3.3 Event Planning Layer

FR-E01
MUST

Create Event

Authenticated customers shall be able to create named Event records with: Title (required), EventType (enum), EventDate (required, must be future date), Location (required), TotalBudget (optional), GuestCount (optional), Notes (optional). Multiple Events per user are supported simultaneously.

UC-10: Customer creates an event plan
FR-E02
MUST

Add EventItem to Event

Customers shall be able to add a Product OR a Package (never both) to an Event as an EventItem. Upon creation, the system shall snapshot SnapshotName, SnapshotPrice, and SnapshotVendorName from the live record. A CHECK constraint enforces exactly one of ProductId or PackageId is non-null.

UC-11: Customer adds service to event plan
FR-E03
MUST

Event Persistence Post-Order

The system shall retain the Event record with Status = Confirmed after an Order is placed. The Order links to the Event via a nullable EventId FK. Deleting an Order shall not cascade to the Event.

FR-E04
MUST

EventItem Status Transitions

EventItem.Status shall transition from Draft → Ordered when included in a placed Order, in the same database transaction as Order creation. An EventItem with Status = Ordered cannot be re-added to a new Order unless the original Order is cancelled.

3.4 Booking & Payment

FR-B01
MUST

Checkout & Order Creation

The system shall allow customers to check out all Draft EventItems in an Event in a single transaction. An Order record is created with Status = Pending. EventId is set on the Order. All included EventItems transition to Ordered. Event.Status transitions to Confirmed.

UC-12: Customer checks out from event plan
FR-B02
MUST

Payment via Gateway

The system shall initiate a payment intent via the Paymob API. On webhook confirmation of payment success, Order.PaymentStatus is updated to Paid and Order.PaymentIntentId is stored. All payment processing is handled server-side. The frontend never handles raw card data.

FR-B03
MUST

Escrow Hold

Upon payment success, funds shall be held in escrow. The system shall record the escrow status in the Order. Vendor payout is not triggered until FR-B05 (delivery confirmation) or FR-B06 (auto-release) is triggered.

FR-B04
MUST

Booking Confirmation Notification

Within 60 seconds of payment confirmation, the system shall send: (a) email confirmation to the customer via SendGrid, (b) SMS notification to the customer via Twilio, (c) in-platform notification to the vendor via SignalR. Both customer and vendor notification records shall be persisted in the database.

FR-B05
MUST

Delivery Confirmation & Payout

Customers shall confirm service delivery via a platform UI action post-event. This triggers escrow release. The system shall initiate vendor payout via the payment gateway within 72 hours. Commission is deducted before disbursement. A payout record with net/gross breakdown is created.

UC-15: Customer confirms delivery
FR-B06
MUST

Auto-Release Escrow

A background job shall run every hour. If an Order's event date has passed by ≥ 48 hours, no dispute exists, and delivery has not been confirmed, the system shall auto-release escrow and trigger vendor payout. Auto-releases are logged as such in the payout record.

FR-B07
MUST

Cancellation Policy Enforcement

The system shall enforce cancellation rules at the application layer: Free if >7 days before event. 25% fee if 2–7 days. Non-refundable if <48 hours. Vendor-initiated cancellation within 7 days triggers full refund + 10% credit. Refund is processed via the payment gateway reverse payment API.

3.5 Vendor Portal

FR-V01
MUST

Vendor Onboarding Submission

The system shall provide a multi-step vendor onboarding form allowing submission of: BusinessName, Address, Description, PortfolioLink, YearsInBusiness, service categories, Products/Packages with pricing, and business license document (PDF upload to Azure Blob). Submitted vendors are created with IsVerified = false and invisible to customers until ops approval.

FR-V02
MUST

Availability Calendar Management

Authenticated vendors shall be able to mark dates on their calendar as Available, Booked, or Blocked. Calendar updates are written to the database and the Redis availability cache. Cache invalidation must occur within 60 seconds of any calendar change. Double-booking of the same date is prevented at the database constraint level.

FR-V03
MUST

Booking Acceptance / Decline

Vendors shall receive a real-time SignalR notification upon new booking. The vendor dashboard shall display a pending booking queue. Vendors shall accept, decline (with mandatory reason field), or request modification within 24 hours. Expiry of the acceptance window with no action auto-accepts the booking.

FR-V04
SHOULD

Vendor Analytics Dashboard

For Standard and Premium subscription tier vendors, the system shall expose a dashboard endpoint returning: booking count (30/60/90 day), profile view count, revenue earned (gross/net), average rating trend, and conversion rate (profile views to bookings).

FR-V05
MUST

Subscription Tier Management

The system shall allow vendors to select, upgrade, or downgrade their subscription tier. Subscription billing is managed via the payment gateway's recurring billing API. Tier changes take effect at the next billing cycle. Features available per tier are enforced server-side on API responses.

3.6 Operations & CRM

FR-O01
MUST

Vendor Review & Approval CMS

Admin-role users shall be able to view all pending vendor submissions in an internal dashboard. For each submission they can: approve (sets IsVerified = true, profile goes live), reject (with reason, vendor notified by email), or request additional information. All actions are audit-logged.

UC-20: Ops approves a vendor
FR-O02
MUST

AI Chatbot Integration

The customer portal shall embed an AI chatbot powered by the OpenAI API. The chatbot context includes EpicHub policy, FAQ, and the authenticated user's active bookings. Responses with confidence below threshold (configurable, default 0.75) shall be flagged for escalation to the human agent queue via SignalR.

FR-O03
MUST

Dispute Management

The system shall allow customers to raise a dispute within 48 hours of the event date. A dispute record is created, escrow is frozen, and both parties are notified. Admin users can view dispute details, attached evidence files (uploaded to Azure Blob), and issue a resolution decision. Resolution triggers the appropriate payment action.

FR-O04
SHOULD

Loyalty Points Engine

The system shall credit loyalty points to a customer's account upon delivery confirmation (not booking). Point balance is stored in the database. Points expire after 12 months via a scheduled background job. Point redemption is applied as a discount at checkout, capped at 30% of booking value combined with any promo code.

FR-O05
SHOULD

Post-Event Survey

A background job shall trigger a survey notification to customers 24 hours after the event date for all completed bookings. Survey responses (star rating + text) are stored and linked to the booking. A review is created from the survey response after admin moderation. One review per booking maximum.

FR-O06
SHOULD

Promotions Engine

Admin users shall be able to create promotional campaigns via the CMS with: discount percentage or fixed amount, applicable categories, eligible user segment, start/end datetime, and maximum redemption count. No developer deployment is required to activate or deactivate a promotion.

04

Non-Functional Requirements

Non-functional requirements define quality attributes — measurable, testable system properties. Each NFR has an associated acceptance test in the Process Documentation.

⚡ Performance
NFR-P01

Customer-facing pages must achieve Time to Interactive (TTI) on a simulated 4G mobile connection. ≤ 3 seconds

NFR-P02

Search API endpoint (/api/v1/vendors/search) must return results under standard load (100 concurrent users). ≤ 2 seconds P95

NFR-P03

Booking confirmation flow (payment → order creation → notification dispatch) must complete end-to-end. ≤ 5 seconds

NFR-P04

Vendor calendar availability change must propagate to customer-facing search results. ≤ 60 seconds

NFR-P05

Lighthouse Performance score on customer homepage and search results page. ≥ 80

🔒 Security
NFR-SEC01

All data at rest in SQL Server and Azure Blob storage must use encryption. AES-256

NFR-SEC02

All client–server communication must use TLS protocol. TLS 1.3

NFR-SEC03

JWT access token expiry. Refresh token stored as httpOnly cookie. 15 min access / 7 day refresh

NFR-SEC04

Zero OWASP Top 10 critical or high severity vulnerabilities at time of production release, verified by penetration test.

NFR-SEC05

All API inputs validated via FluentValidation before any database operation. SQL injection prevention via EF Core parameterized queries only.

🟢 Reliability & Availability
NFR-R01

Platform uptime on a rolling 30-day basis. Measured via Azure Monitor. ≥ 99.5%

NFR-R02

Planned maintenance windows restricted to 02:00–05:00 Cairo time with 48-hour advance notice.

NFR-R03

Database point-in-time recovery capability. RPO (Recovery Point Objective). ≤ 1 hour

NFR-R04

Payment webhook processing must be idempotent — duplicate webhook delivery must not create duplicate Orders or payouts. Idempotency keys required on all payment operations.

📈 Scalability
NFR-SC01

The system must handle 10× baseline load without architectural redesign. Baseline defined as 500 concurrent users. 5,000 concurrent users max

NFR-SC02

Adding a new MENA geographic market must require zero changes to core API or database schema. Market isolation via market_id discriminator columns where applicable.

♿ Accessibility & Compatibility
NFR-AC01

Web Accessibility standard for all customer-facing pages, verified by aXe automated testing. WCAG 2.1 Level AA

NFR-AC02

Full functionality across mobile ≥ 320px, tablet ≥ 768px, desktop ≥ 1280px. No horizontal overflow on any tested viewport.

NFR-AC03

Angular i18n framework integrated from Day 1. Arabic RTL layout must be activatable in Phase 2 without structural code changes.

05

Interface Requirements

5.1 External System Interfaces

💳

Payment Gateway — Paymob

REST API integration via HTTPS. Payment intent creation, webhook receipt for status updates, refund initiation, and recurring subscription billing. All communication server-to-server. Frontend never receives raw keys.

🤖

AI Chatbot — OpenAI API

Chat Completions API. System prompt includes EpicHub FAQ and current user context. Streamed responses displayed in real-time in chatbot UI. Confidence scoring used for escalation routing.

📧

Email — SendGrid

Transactional email for: registration verification, booking confirmations, payout notifications, dispute updates, survey triggers. Dynamic templates managed in SendGrid. All sends logged in the database.

📱

SMS — Twilio

SMS notifications for: booking confirmation, vendor acceptance, payout complete. Egypt long code used. Delivery receipts tracked and stored against notification records.

🗺️

Google Maps & Places API

Maps SDK embedded in Angular for venue location display. Places Autocomplete for location input fields. Geocoding for distance-based search filtering. Client-side API key (restricted to epichub.com domain).

☁️

Azure Blob Storage

Used for: vendor portfolio images, vendor license document uploads, dispute evidence files. All blobs served via Azure CDN. SAS tokens used for upload. Public read access for portfolio images only.

5.2 Communication Interfaces

All API communication uses HTTPS REST (JSON, UTF-8). Real-time notifications use SignalR over WebSocket (fallback to Long Polling). File uploads use multipart/form-data. All API endpoints are versioned at /api/v1/. API documentation auto-generated via Swagger/OpenAPI 3.0.

06

System Constraints

6.1 Design Constraints

DC-01

Mandated Backend Stack

Backend must be ASP.NET Core (.NET 8) with Entity Framework Core. No alternative ORM or non-.NET runtime is permitted.

DC-02

Mandated Frontend Stack

Frontend must be Angular 17+ with TypeScript. React, Vue, or other SPA frameworks are not permitted for any Phase 1 deliverable.

DC-03

Azure Cloud Hosting

All infrastructure must be hosted on Microsoft Azure. No AWS or GCP resources are permitted for Phase 1.

DC-04

RESTful API Design

All API endpoints must conform to RESTful conventions. GraphQL, gRPC, or RPC-style APIs are not permitted for Phase 1.

DC-05

Code-First Database Migrations

All database schema changes must be managed via EF Core code-first migrations. No manual SQL schema scripts are permitted in production deployments.

6.2 Business Constraints

Phase 1 is restricted to the Egypt market only. Arabic RTL, native mobile apps, BNPL payments, and corporate enterprise module are explicitly out of scope for Phase 1. See BRD for full business constraint list.
