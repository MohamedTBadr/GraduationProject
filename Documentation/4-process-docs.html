SDLC Overview

EpicHub follows an Agile Scrum methodology with 2-week sprints. The team maintains a single prioritized Product Backlog. Each sprint produces a shippable increment deployed to the Staging environment.

📋
PHASE 01

Planning

SRS, Architecture, API contracts, entity schema, sprint 0 backlog grooming

🏗️
PHASE 02

Development

TDD backend, Angular components, daily standups, 2-week sprints, code review

🧪
PHASE 03

Testing

Unit → integration → E2E → performance → security pen test → UAT

🚀
PHASE 04

Deployment

Staging validation → slot swap → production → monitoring & alerting active

📊
PHASE 05

Operations

Azure Monitor dashboards, incident response, on-call rotation, sprint retrospectives

03

Git Workflow

EpicHub follows a simplified Git Flow branching strategy. All code changes require a Pull Request with at least one approval. Direct pushes to main and develop are blocked by branch protection rules.

// Branch Model
mainProduction-ready code only. Tagged with version on each release. Auto-deploys to Production slot on merge via GitHub Actions.
developIntegration branch. All feature branches merge here. Auto-deploys to Staging on each merge. Must pass all CI checks to merge.
feature/{ticket-id}-{short-desc}One branch per ticket. Branched from develop. E.g. feature/EH-142-event-item-snapshot. PR to develop. Squash merge on approval.
hotfix/{ticket-id}-{desc}Production hotfix only. Branched from main. PR to both main AND develop simultaneously. Merges trigger emergency deploy pipeline.

Commit Message Convention

# Format: <type>(<scope>): <short description>
feat(event): add snapshot logic to EventItem creation
fix(auth): refresh token not cleared on logout
test(booking): add unit tests for checkout atomic transaction
refactor(vendor): extract matchmaking score to separate service
docs(api): update checkout endpoint response schema
chore(infra): add Redis connection string to Key Vault
# Types: feat | fix | test | refactor | docs | chore | perf | ci
# Scopes: auth | event | vendor | booking | payment | ops | infra | ui

Test cases are organized by type: Unit (service + business logic isolation), Integration (API endpoints with test database), E2E (Cypress browser automation), Performance (k6 load), and Security. Each traces to an FR or NFR from the SRS.

Assert: eventItem.SnapshotPrice == 500.00

Unit
Pass

EventService — CHECK constraint: both ProductId and PackageId null throws

Unit
Pass

BookingService — EventItem transitions to Ordered on checkout

Unit
Pass

EscrowService — Commission deducted before vendor payout

Definition of Done

A user story or task is only marked Done when ALL items in the relevant checklist are complete. "Code written" is not Done.

📦 Feature / Story
  • Code written, reviewed, and approved by at least one team member
  • Unit tests written and passing — code coverage gate maintained (≥ 75%)
  • Integration tests written for all new API endpoints
  • API documentation updated in Swagger comments and Postman collection
  • No new compiler warnings or Roslyn analyzer warnings introduced
  • Feature deployed to Staging and manually smoke-tested by developer
  • PO has accepted the story against acceptance criteria in Staging
  • Linked ticket moved to Done in project board
🚀 Sprint Release
  • All sprint stories meet the Feature DoD above
  • Regression test suite passes in full on Staging (all existing tests green)
  • No P0 or P1 open bugs — P2 bugs accepted only with PO sign-off
  • Lighthouse score ≥ 80 on all changed pages
  • Sprint velocity recorded and burndown chart completed
  • Retrospective actions from previous sprint tracked and actioned
  • Release notes written — what changed, what was fixed, known issues
🏭 Production Release
  • Full E2E Cypress suite passes on Staging
  • Load test (k6) passes all NFR thresholds: P95 < 2s search, P95 < 5s checkout
  • Penetration test completed — zero critical or high findings open
  • All BAC (Business Acceptance Criteria from BRD) signed off by PO
  • Azure Monitor dashboards and alerts configured and tested
  • On-call rotation assigned with incident response runbook published
  • Database backup verified — point-in-time restore tested
📝 Documentation
  • Any new API endpoint documented in Swagger + Postman collection updated
  • Any architecture decision recorded in decision log with rationale
  • New entity or schema change reflected in entity schema reference doc
  • User-facing feature has corresponding user documentation update
  • CHANGELOG.md updated with version entry
  • README updated if setup steps, environment variables, or dependencies change
