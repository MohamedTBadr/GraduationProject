01

Architecture Overview

EpicHub follows a layered, clean architecture pattern. The system is divided into four logical layers: Presentation, API, Application/Service, and Data. Each layer has a single direction of dependency — upper layers depend on lower layers, never the reverse.

Key Architectural Decision

The planning layer (Event / EventItem) and financial layer (Order / OrderItem) are deliberately separated. Event records persist independently — they are never deleted when an Order is cancelled. Order.EventId is a nullable FK so Orders can exist without an Event (legacy support). This separation is the central architectural decision in the data model.

Architecture Principles

🧱

Separation of Concerns

Each layer owns exactly one responsibility. Controllers route. Services orchestrate. Repositories persist. No business logic in controllers or data models.

🔄

Dependency Inversion

All service and repository dependencies are injected via interfaces. No concrete class instantiation across layer boundaries. Registered in ASP.NET DI container at startup.

📦

Repository Pattern

All database access goes through typed repository interfaces. EF Core DbContext is never directly called from service layer. Enables unit testing with in-memory database.

⚡

Cache-Aside Pattern

Redis used as an aside cache for vendor availability and search results. Cache is populated lazily and invalidated explicitly on writes. No write-through pattern.

2.3 Service Layer

📅

EventService

Creates/updates Events and EventItems. Enforces snapshot logic: reads Product/Package name+price at EventItem creation time, stores in snapshot fields.

💳

BookingService

Orchestrates checkout: creates Order + OrderItems, transitions EventItem statuses, calls PaymentService, emits SignalR notification. All in a single database transaction.

🏦

EscrowService

Manages escrow state on Orders. Triggered by: payment webhook, delivery confirmation, auto-release job, dispute resolution. Calls PayoutService after deducting commission.

🔔

NotificationService

Dispatches notifications via SendGrid (email), Twilio (SMS), SignalR (in-platform). All notification attempts are persisted with delivery status. Retries on failure (3 attempts, exponential backoff).

🤖

ChatbotService

Manages OpenAI conversation context per user session. Applies confidence threshold for escalation. Routes escalations to the human agent SignalR group. Persists conversation history.

🔍

SearchService

Builds vendor search queries with EF Core LINQ. Applies matchmaking scoring. Reads availability from Redis cache. Writes results to Redis with 5-minute TTL.

2.4 Data Layer — SQL Server + Redis

Primary persistence: Azure SQL Server via EF Core code-first. All schema changes via migrations (never manual SQL). Redis used for: vendor availability cache (TTL 60s), search results cache (TTL 5min), SignalR backplane, session data.

05

Design Patterns

Repository Pattern

Generic IRepository<T> interface with typed implementations (VendorRepository, EventRepository, etc.). Injected via constructor DI. AppDbContext only instantiated in repository implementations.

Unit of Work

IUnitOfWork wraps AppDbContext.SaveChangesAsync(). Services call UoW.CommitAsync() to persist. Enables atomic multi-repository operations in a single database transaction.

Cache-Aside

Services check Redis before hitting SQL. On cache miss, populate Redis after SQL read. On writes, invalidate relevant cache keys explicitly. Used for: vendor availability, search results, session tokens.

Snapshot Pattern

EventItem captures immutable price, name, and vendor name at creation time. OrderItem captures same at checkout. Prevents historical records being corrupted by future vendor edits — critical for financial integrity.

Observer (Domain Events)

Domain events (BookingConfirmed, DeliveryConfirmed, DisputeRaised) dispatched via MediatR. Handlers for each event trigger notifications, escrow state changes, and audit log entries decoupled from business logic.

Strategy (Payment Gateway)

IPaymentGateway interface with PaymobGateway and StripeGateway implementations. Gateway is selected at runtime via configuration. Enables zero-code failover between providers.

06

Security Architecture

🔑 Authentication

JWT issued on login. Access token (15min) in Authorization header. Refresh token (7d) in httpOnly cookie. ASP.NET Identity manages password hashing (BCrypt). OAuth via Google provider linked to local user.

🛡️ Authorization

Role-based claims: Customer, Vendor, Admin. [Authorize(Roles="...")] on all protected controllers. Resource-level authorization: vendors can only modify their own resources (checked in service layer, not just controller).

🔒 Data Encryption

SQL Server transparent data encryption (AES-256). Azure Blob Storage server-side encryption. All transport via TLS 1.3. PII fields (email, phone) encrypted at column level in production.

💉 Input Validation

FluentValidation validates every API request before handler execution. Validation pipeline registered as MVC action filter. All user-supplied content is sanitized before persistence. EF Core parameterized queries prevent SQL injection.

🪝 Webhook Security

Payment gateway webhooks verified via HMAC-SHA256 signature against a secret key. Requests failing HMAC verification are rejected with 401. Webhook idempotency enforced via PaymentIntentId uniqueness constraint.

📋 Audit Logging

All admin actions (vendor approval, dispute resolution, promotion creation) are audit-logged with: actor UserId, action type, affected entity ID, timestamp, and IP address. Audit log is append-only and never modified.
